# 서비스 계층 중심 설계 vs 도메인 중심 설계

이번 주차에는 빈약한 도메인 모델에서 도메인 모델 패턴으로 진화하는 과정을 수행하였습니다.

## 1. 변경 전: 서비스 계층에 비즈니스 로직이 집중된 구조 (빈약한 도메인 모델)
- **특징**: 기존 서비스 계층의 메서드를 보면 수량 검증, 판매 상태 확인, 재고 부족 여부 검사, 재고 차감, 품절 상태 변경까지 모든 비즈니스 로직을 서비스 계층이 직접 처리하고 있습니다.
- **엔티티의 역할**: 기존 엔티티 계층에는 `@Setter`가 열려 있으며, 비즈니스 로직을 전혀 갖지 못한 채 단순히 데이터를 담고 있는 수동적인 컨테이너 역할만 수행합니다.
- **문제점**: 이러한 구조는 로직이 서비스에 종속되어 재사용성이 떨어지며, 코드 곳곳에서 `setStock()`, `setStatus()`를 무분별하게 호출할 수 있어 객체의 일관성과 안전성이 쉽게 훼손됩니다.

## 2. 변경 후: 엔티티가 비즈니스 로직을 주도하는 구조 (도메인 모델 패턴)
- **특징**: 개선된 서비스 계층에서는 상품을 조회하고, 엔티티에게 "재고를 차감해라"라고 명령을 내린 뒤, 저장하는 3줄의 흐름 제어(오케스트레이션)만 담당합니다.
- **엔티티의 역할**: 개선된 엔티티 계층에서 `@Setter`를 제거하여 외부의 무분별한 상태 변경을 차단했습니다. 대신 `decreaseStock`이라는 의미 있는 비즈니스 메서드를 통해, 객체 스스로 유효성을 검증하고 자신의 상태(재고, 판매 상태)를 안전하게 변경합니다.
- **장점**: 객체지향의 핵심인 **캡슐화**가 제대로 이루어졌습니다. 서비스 계층이 얇고 깔끔해지며, 상태 변경에 대한 모든 책임과 테스트 포인트가 엔티티 한 곳으로 모여 유지보수성이 크게 향상됩니다.

## 3. 느낀점
- 저번 프로젝트에서 오늘 배운 도메인 비즈니스 메서드를 사용해 객체를 업데이트하고 이것에 더해 정적 팩토리 메서드를 사용해 객체를 만들어 `@Setter`를 완벽히 지웠었는데 이를 복습할 수 있는 기회가 되었다.
