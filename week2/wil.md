# DDD 도메인 엔티티 설계 및 구현

이번 주차에서는 도메인 주도 설계(DDD)의 핵심 개념들을 적용하여, 별도의 Service 계층 없이 테스트 코드의 요구사항을 자체적으로 충족하는 도메인 엔티티 로직을 구현했습니다.

#### 1. Entity vs Value Object (값 객체)
*   **개념 적용:** 식별자(ID)를 기준으로 동등성을 판단하는 Entity와 달리, 속성 값 자체가 식별 기준이 되는 Value Object의 특성을 살려 도메인을 분리했습니다.
*   **코드 구현 (`Money`, `Quantity`):**
    *   `Money`와 `Quantity` 클래스를 식별자가 없는 `@Embeddable` 값 객체로 정의했습니다.
    *   테스트 코드(`MoneyTest.java`, `QuantityTest.java`)의 요구사항에 맞춰 값 객체의 불변성을 보장했습니다. 예를 들어, `Money`의 `add` 연산 시 기존 객체의 값을 직접 수정하는 것이 아니라 계산된 값을 가진 새로운 `Money` 인스턴스를 반환하여 "더해도 원래 금액은 바뀌지 않는다"는 테스트를 통과하도록 구현했습니다.

#### 2. 불변식(Invariants) 유지와 정적 팩토리 메서드
*   **개념 적용:** 객체가 생성될 때와 살아있는 동안 항상 유효한 상태를 유지하도록 강제하는 '불변식'을 정의하고, 이를 보호하기 위해 정적 팩토리 메서드 패턴을 활용했습니다.
*   **코드 구현:**
    *   `Money`와 `Quantity`의 생성자를 `private`으로 제한하여 무분별한 객체 생성을 막았습니다.
    *   생성자 내부에서 "금액은 0원 이상이어야 한다", "수량은 1개 이상(0 이하나 음수 불가)이어야 한다"는 불변식 검증 로직을 단일화하여 배치하고, 위반 시 `IllegalArgumentException`을 발생시키도록 구현했습니다.
    *   유효성 검증을 통과한 안전한 객체는 오직 `Money.of()`, `Quantity.of()`와 같은 명시적인 정적 팩토리 메서드를 통해서만 반환되도록 강제했습니다.

#### 3. Aggregate Root (주문, Order) 중심의 캡슐화 및 상태 제어
*   **개념 적용:** 연관된 객체들(`OrderItem`, `Money`, `Quantity`)을 하나의 단위(Aggregate)로 묶고, 외부에서는 오직 Root 엔티티(`Order`)를 통해서만 내부 상태에 접근하거나 변경하도록 설계했습니다.
*   **코드 구현 (`OrderTest.java`, `Order.java` 기반):**
    *   **생성 시점의 무결성 보장:** `Order.place()` 정적 팩토리 메서드를 통해 "항목 없이는 주문할 수 없다"는 비즈니스 규칙을 강제하여, 인자가 `null`인 경우 예외를 던지도록 초기화 단계를 통제했습니다.
    *   **도메인 상태 스스로 검증:** "배송이 시작되면 항목을 추가할 수 없다", "배송이 시작되거나 완료된 주문은 취소할 수 없다"는 테스트 요구사항을 만족하기 위해, `addItem()`, `cancel()` 호출 시 `Order` 엔티티 스스로 현재의 `OrderStatus`를 판별하여 조건 불만족 시 `IllegalStateException`을 발생시키도록 기능을 내재화했습니다.
    *   **객체 간 협력에 의한 총액 계산:** 주문 총액(`totalAmount()`) 계산 로직을 외부에 두지 않고, `Order` 객체가 자신의 `orderItems`를 순회하며 개별 `OrderItem`의 `subtotal()` 연산 결과를 취합(reduce)하는 방식으로 위임 구조를 완성했습니다.
    *   **외부의 강제 수정 차단:** 외곽 로직에서 `order.getOrderItems().clear()`를 시도하여 내부 항목을 임의 조작하려는 시도를 막기 위해, `getOrderItems()` 호출 시 `Collections.unmodifiableList()`로 감싼 불변 리스트를 반환하여 Aggregate Root의 내부 상태를 안전하게 보호했습니다.
