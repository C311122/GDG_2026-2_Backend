# 4주차 WIL: 동시성 제어 (낙관적 락 vs 비관적 락)

## 1. 동시 주문 테스트 결과 분석

### Q1. 테스트를 여러 번 실행했을 때 성공·실패 건수와 최종 재고 비교

- **테스트 결과**: `성공=1, 실패=9, 최종 재고=4`
- **이유**: 낙관적 락(`@Version`)은 DB에 락을 걸지 않고 커밋 시점에 버전을 비교한다. 여러 스레드가 동시에 같은 버전을 읽으면 가장 먼저 커밋한 트랜잭션만 성공하고, 동시에 같은 버전을 읽었던 나머지 트랜잭션들은 버전 불일치로 실패한다. 스레드 실행 타이밍에 따라 새로운 버전을 읽는 시점이 달라지므로 결과에 차이가 발생할 수 있다.

### Q2. 실패한 주문의 원인: 낙관적 락 충돌 vs 재고 부족의 차이

- **낙관적 락 충돌**: 재고가 아직 남아있음에도(최종 재고 4개), 여러 트랜잭션이 동시에 같은 데이터를 수정하려다 버전이 어긋나 발생한 **동시성 충돌 실패**다.
- **재고 부족 (도메인 예외)**: 동시성 충돌과 무관하게 실제 남은 재고가 0개여서 더 이상 차감할 수 없는 **비즈니스 규칙 위반 실패**다.

## 2. 추가 탐구: 낙관적 락 재시도 로직과 비관적 락 비교

### 1) 충돌한 요청을 어떻게 다시 시도하도록 만들 수 있을까?

- **서버 측 자동 재시도**: Spring Retry(`@Retryable`)나 반복문(try-catch)을 사용해 `ObjectOptimisticLockingFailureException` 발생 시 짧은 대기 시간(Backoff) 후 트랜잭션을 새로 시작한다.
- **클라이언트 측 재시도**: `GlobalExceptionHandler`를 통해 **HTTP 409 Conflict**를 응답하고, 클라이언트가 재요청하도록 유도한다.

### 2) 재시도한다면 몇 번까지 시도해야 할까?

- 무한 재시도는 DB 부하와 스레드 고갈을 유발하므로 보통 **3~5회 내외**로 제한하고, 재시도 간격에 점진적 지연(Exponential Backoff)을 두는 것이 적절하다.

### 3) 낙관적 락 대신 비관적 락을 사용한다면 어떤 차이가 있을까?

- **낙관적 락**: DB 락을 걸지 않아 충돌이 적을 때 성능이 좋지만, 충돌이 잦으면 실패 및 재시도 비용이 커진다.
- **비관적 락 (`PESSIMISTIC_WRITE`)**: 조회 시점부터 DB 행에 락(`SELECT ... FOR UPDATE`)을 걸어 트랜잭션을 순차 처리한다. 대기 시간은 발생하지만 충돌로 인한 실패 없이 재고 5개가 정확히 모두 소진(`성공=5, 실패=5(재고 부족), 최종 재고=0`)된다.
